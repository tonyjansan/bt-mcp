# BT-MCP v0.6 规划与设计

日期：2026-11-11 · 基线：v0.5.x · 前置：[roadmap-v0.5.md](roadmap-v0.5.md)

## 0. 先看事实：v0.5 教会我们什么

v0.5 做了 8 项任务，全部有代码与测试证据，但过程中的**发现**比任务清单更有价值：

| 发现 | 含义 |
|---|---|
| 官方 SDK 互验抓到「pipe 传输没重组分片」 | 协议**逻辑**对、**集成**错。前三层验证（差分/结构/golden）都看不见 |
| 差分抓到「只改了一侧严格 JSON」 | 差分是**唯一**能发现「两侧漂移」的手段，但它必须覆盖到新配置 |
| 共享模式差分第一次是红的 | 原因是 C `MAX_REASM=1` vs Rust `4`——**容量也必须对齐**，否则差分的红是噪音 |
| 边界测试抓到 3 处 NULL 解引用崩溃 | 「正常流程全绿」和「畸形输入不崩」是两件事 |
| 分支覆盖率努力了一天只从 58% 到 67% | 最后 8pp 需要**组合爆炸**级测试，成本陡增 |

**结论**：v0.6 的主线不该是「再加功能」，而是**把验证从"人工设计的用例"推进到"自动生成的对抗"**，
同时补掉三处被这一轮暴露出来的结构性缺口。

---

## 1. 主题：**自动化对抗与规模验证**

v0.4 靠人写用例发现 5 个缺陷，v0.5 靠人写用例 + 第三方 SDK 发现 5 个缺陷。
人工用例的边际收益在明显下降（分支覆盖率一天只涨 9pp）。v0.6 要换引擎。

### P0（三个结构性问题，必须先解决）

| # | 任务 | 为什么现在必须做 | 设计要点 |
|---|---|---|---|
| **N1** | **组合矩阵 + 逐点故障注入** | V3 未达标的唯一原因。432 个未覆盖分支集中在「方法 × 参数 × 失败点」 | 用**表驱动**代替手写用例：方法列表 × 参数形态列表（缺失/错类型/超长/嵌套/越界）× 失败点（第 N 次写入失败）自动生成用例；断言"返回码属于该方法的允许集合"而不比对具体输出。这是能用几十行生成上千用例的结构 |
| **N2** | **双向 fuzz 通道（结构感知）** | 现在的 fuzz 只打帧层字节，L5 只看固定语料 | 用**语法感知**的变异器（保留 JSON 骨架、只变异字段值/嵌套/顺序）打 `server_rx`，配合「不崩溃 + 返回码合法 + 状态可继续」三条不变量；跑 24h 不崩才算出师 |
| **N3** | **差分矩阵正交化** | 共享模式那份红暴露了矩阵是手写的，漏一个维度就是假绿 | 把 (FCS16, MAX_REASM, MTU, 通道类型, 协议版本) 变成**笛卡尔积自动生成**的矩阵；每个维度在两侧配置里显式声明，不一致就直接 fail（而不是等差分红了再猜） |

### P1（规模与真实链路）

| # | 任务 | 设计要点 |
|---|---|---|
| **N4** | **多会话 × 多线程压测** | 目前 2 实例 2 线程 200 轮。扩展到 4 实例 × 4 线程 × 10k 轮 + 随机断链/重连，验证 pool 分派与 RTO 在长时间下的稳定性 |
| **N5** | **真实 BLE HIL（Linux/BlueZ）** | 目前 HIL 是应用层模拟（198 项）。接 BlueZ 后能验证真实 MTU 协商、连接间隔、丢包模式；这是唯一能证伪「我们假设的 BLE 行为」的手段 |
| **N6** | **链路仿真器** | 可配置的 (延迟分布, 丢包率, 乱序率, 突发丢包) 模型，跑**回归化的 soak**（如 30 分钟模拟 = 数万条消息），断言不变量而不是逐字节 |
| **N7** | **RAM/CPU 预算门禁** | 已有 bench；扩展成「每档位的静态 RAM + 每消息 CPU 周期」基线，CI 里 fail-on-regression（共享缓冲那次 41KB→16KB 的收益应被自动守住） |

### P2（能力补齐，按需）

| # | 任务 | 说明 |
|---|---|---|
| **N8** | `resources/templates/list`、`completion/complete` | 规范里尚未实现的两个方法 |
| **N9** | sampling 完整语义 | `modelPreferences`、多轮 sampling、取消传播 |
| **N10** | 真实平台 port | Zephyr/NimBLE、ESP-IDF 各一份可编译示例 + 上板验证 |
| **N11** | CMake/Makefile/pkg-config + amalgamation | 降低集成成本；WASM 模拟器便于 Host 开发者本地联调 |
| **N12** | 8/16 位 MCU 收敛 | `uint64_t` → `uint32_t` 分段（进度计数、writer u64） |
| **N13** | MISRA-C / 静态分析基线 | clang-tidy + cppcheck，把「零告警」变成门禁 |
| **N14** | 文档自动化 | doxygen API、`UPGRADING.md`、**协议草案从公开头文件生成**（防漂移——v0.3 就吃过文档与实现不一致的亏） |

## 2. 关键设计草案

### 2.1 N1：表驱动组合矩阵

```c
/* 方法 × 参数形态 自动生成用例，而不是手写 */
static const char *const METHODS[] = {
    "initialize", "ping", "tools/list", "tools/call", "resources/list",
    "resources/read", "resources/subscribe", "prompts/list", "prompts/get",
    "logging/setLevel", "notifications/cancelled", /* 新增方法必须加进来 */
};
static const param_shape_t SHAPES[] = {
    { .desc = "缺失",     .json = NULL },
    { .desc = "null",     .json = "null" },
    { .desc = "空对象",   .json = "{}" },
    { .desc = "错类型",   .json = "[]" },
    { .desc = "坏 URI",   .json = "{\"uri\":\"x\"}" },
    { .desc = "超长字段", .json = "{\"name\":\"<300 字符>\"}" },
    { .desc = "嵌套超限", .json = "{\"a\":[[[[[[[[1]]]]]]]]}" },
};
/* 失败点：第 N 次写入失败（N=0 表示不失败） */
for (each method) for (each shape) for (N in {0,1,2,3,8,64}) {
    rpc = build(method, shape);
    expect_rc = allowed_set(method, shape);   /* 只断言"合法错误码"，不比对字节 */
    assert(server_rx(rpc) in expect_rc || expect_rc == ANY);
}
```

**为什么用「允许集合」而不是精确期望**：精确期望要人写 11×7×6 ≈ 460 个，
维护成本爆炸；而「不得崩溃 + 只能是哪几个码」已经能抓住绝大多数缺陷
（v0.5 抓到的 3 个 NULL 崩溃就是这么来的）。

### 2.2 N2：语法感知 fuzz

现有 `fuzz_frame.c` 变异字节。L5 需要的是**结构变异**：

```
保留外壳 {"jsonrpc":"2.0",  ___, "method":___ }，变异：
  - 字段值类型轮换（string ↔ number ↔ array ↔ object ↔ null）
  - 嵌套深度随机 1..12
  - 字符串内容随机（含未转义引号、\u 非法、超长、UTF-8 边界）
  - 键顺序打乱、重复键、超长键
  - 尾部结构（合法空白 / 垃圾 / 第二个对象 / 截断）
不变量：rc ∈ 允许集合；同一实例可继续服务下一条（状态不粘）；
        内存不增长（长时间跑 RSS 曲线平稳）
```

### 2.3 N3：正交差分矩阵

```python
DIMS = {
  "FCS16":      [0, 1],
  "MAX_REASM":  [1, 4],       # 与 SHARED_REASM 联动
  "MTU":        [23, 53, 244, 517],
  "channel":    ["packet", "stream"],
  "proto":      ["2025-03-26", "2025-06-18", "2025-11-25"],
}
# 自动生成组合；每侧构建时显式打印自己的配置，
# harness 先比对配置签名（不一致直接 fail，而不是跑完才发现红）
```

**关键改进**：加「配置签名比对」前置检查。v0.5 那次共享模式差分红了，
排查花了时间才意识到是容量不匹配——有签名比对就是一句话的事。

## 3. 完成定义（v0.6）

1. 分支覆盖率 ≥ 80%（N1 的表驱动应能一次跨过 75%）。
2. L5 结构感知 fuzz 连续 24 小时（或 2000 万次变异）零崩溃、零内存增长。
3. 差分矩阵覆盖 5 维笛卡尔积（≥ 96 组合），每组合 ≥ 200 随机脚本，全绿且配置签名自动校验。
4. 真实 BlueZ HIL 跑通三类场景：MTU 协商、连接中断恢复、突发丢包。
5. soak：30 分钟链路仿真（≥ 5 万条消息）零不变量违反。
6. RAM/CPU 基线纳入 CI，回归即失败。

## 4. v0.5 遗留项的明确交接

| 遗留 | 交接给 | 说明 |
|---|---|---|
| 分支覆盖率 67.1% → 75% | **N1** | 表驱动组合矩阵是唯一可行路径，手写用例边际收益已耗尽 |
| `resources/templates/list` / `completion/complete` | N8 | 规范内方法，实现成本低但需要新的注册表 |
| sampling 完整语义 | N9 | 当前只有承载能力（`server_request`），缺 `modelPreferences` 与多轮 |
| 平台 port | N10 | HIL 目前是应用层模拟，无法证伪真实 BLE 行为假设 |

## 5. 建议执行顺序

```
Week 1–2: N1（表驱动矩阵）→ 预期分支直接过 75%，并顺带清掉一批未发现缺陷
Week 2–3: N3（正交矩阵 + 签名比对）→ 让"假绿"不可能发生
Week 3–5: N2（结构感知 fuzz）→ 长跑 + 内存曲线
Week 5–7: N5/N6（真实 HIL + 链路仿真 soak）
Week 7+:  N7 → N8/N9 → N10/N11/N14
```

理由：**先要度量（N1/N3），再要对抗（N2），最后才是规模（N5/N6）**。
v0.5 的教训是：没有度量时，人的直觉会把时间花在低收益的地方
（分支覆盖率手写一天只涨 9pp 就是证据）。
