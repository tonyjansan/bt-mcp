BT-MCP v0.9.1 外部接口规约

蓝牙承载 MCP 协议栈 · Proxy / Host 集成者文档 · C99 平台无关内核 · 2026-11-11 · v0.6

本文面向要把 bt-mcp core 接到真实 GATT / SPP 通道上的宿主（Proxy/Host）开发者。core 自身零厂商假设、零 OS 依赖、无动态分配；宿主的全部职责集中在三件事：① 填通道能力结构体，② 提供一对 emit/送达回调，③ 驱动时钟（tick）。其余协议细节（分片、信用、状态机、JSON-RPC）由 core 内部消化。

零改动集成判例（M4c 实测）：GATT 与 SPP 两种 port 接入同一份 core 源码，core 侧一行未改。两种通道唯一的差异就是 port 填进 bt_mcp_chan_cap_t 的取值。

1分层架构与职责边界

┌───────────────────────────────┐ │ L5 mcp_server │ JSON-RPC 分派（initialize/tools/call…） ├───────────────────────────────┤ │ L4 session │ 状态门 IDLE→LINK_UP→READY、信用窗口、RESUME ├───────────────────────────────┤ │ L3 frame │ 0xB7 分帧 / 重组（协议核心，零 OS 依赖） ├───────────────────────────────┤ ▲ 回调上抛（msg_sink） │ L2 transport（port） │ ← 宿主实现区：bt_mcp_chan_cap_t + emit/送达 └───────────────────────────────┘ ▼ 发射 emit(io, data, len)

依赖严格单向向下：L5→L4→L3→L2；反向数据只经注册回调（上抛 sink、发射 emit）。core 只通过一个结构体 bt_mcp_chan_cap_t 感知通道差异，core 源码中没有任何 vendor ifdef。

2通道能力 bt_mcp_chan_cap_t

core 对通道的全部假设就这一个结构体（core/include/bt_mcp/capability.h）：

typedef enum {
    BT_MCP_CHAN_PACKET = 0, /* 包语义：有 MTU、可能丢、无跨包边界（GATT、CoC） */
    BT_MCP_CHAN_STREAM = 1  /* 流语义：字节流有序可靠（SPP、RFCOMM、UART） */
} bt_mcp_chan_kind_t;

typedef struct bt_mcp_chan_cap {
    bt_mcp_chan_kind_t kind;
    uint16_t mtu;             /* 单次 send payload 上限；流通道填 0 = 无限 */
    uint8_t  reliable   : 1;  /* 1 = 送达有序可靠 */
    uint8_t  flow_ctrl  : 1;  /* 1 = 通道自带流控，L4 免信用 */
    uint8_t  max_pending : 4; /* 建议同时在途消息数（= 对端重组槽数） */
} bt_mcp_chan_cap_t;

GATT notify/writePACKET协商 ATT_MTU−3（未知取 20 保守值）00需 L3 分片 + L4 信用
SPP / RFCOMMSTREAM0（无界）11帧直连发，序号仅作同步
L2CAP LE CoCPACKETCoC MTU11免信用，仅保留分片

3帧格式与分片

3.1 帧头（小端 6B）

0xB7
magic
flags
bit0..2
seq
消息序号 u8
idx
分片号 u8
len (LE u16)
本片 payload 字节
flags 位宏含义
bit0 = 0x01BT_MCP_FLAG_LAST本消息末片
bit1 = 0x02BT_MCP_FLAG_CHUNK本消息分多片（消息首片即置位，控制帧恒单片）
bit2 = 0x04BT_MCP_FLAG_CTRL控制帧（见 §4）
  • seq：发送侧跨消息自增 mod 256；同一消息的全部分片共享同一 seq。
  • idx：分片号严格递增（0,1,2…），重组侧按 next_idx 校验。
  • 协议无 CRC：BLE 链路层/RFCOMM/CoC 已含校验；流通道失步由 magic+len 语法校验承担。无链路校验的自定义 UART 可编译期置 BT_MCP_CFG_FCS16=1 追加 2 字节 CRC16-CCITT。

3.2 两条通道的分片行为差异（M4c 实测判例）

流通道（SPP）包通道（GATT）
发送形态单帧承载整条消息（len ≤ 8192），无分片按 min(mtu, 255) 分多片，每片独立帧头
emit 次数1 帧 = 2 次 emit（hdr 6B + payload）每片 2 次 emit（hdr + payload）
feed 喂法任意字节段（1B~7B 混合切分实测全量重组成功）须按片边界喂（一个 GATT notify 一次 feed）
重组资源流解析器状态机（逐字节语法）重组槽 max_reasm（默认 4）× 8192B
v0.3 起：一个分片 = 一次 emit 调用（帧头与载荷已在 core 内拼好）。宿主直接把 emit 落到 GATT notify / SPP write 即可，无需再做片聚合——v0.2 的「hdr 一次、payload 一次」陷阱已消除。唯一例外是流通道上超过内部栈缓冲（约 261B）的大帧，会拆成「头+载荷」两次 emit，字节流语义下等价。

4控制帧

控制帧（flags bit2=1）恒单片 ≤ 255B，payload 首字节为类型：

type宏参数（payload 后续）方向用途
0x01BT_MCP_CTRL_CREDITu16 累计已消费条数（小端，回绕安全）双向包通道信用回补
0x02BT_MCP_CTRL_PINGu8 epoch双向活性探测
0x03BT_MCP_CTRL_RESUME_REQu32 tokenC→S会话恢复请求
0x04BT_MCP_CTRL_RESUME_OKu32 tokenS→C恢复确认
0x05BT_MCP_CTRL_RESUME_REJu8 reasonS→C恢复拒绝（token 已作废）

宿主一般不直接构造控制帧——用 bt_mcp_session_ctrl() 发、由 bt_mcp_session_rx() 收并内部消化（见 §6.2）。

v0.3 新增两个控制帧，仅 cap.reliable == 0 的包通道使用：

type宏参数用途
0x06BT_MCP_CTRL_ACKu8 seq消息级确认，释放对端重传槽
0x07BT_MCP_CTRL_NACKu8 seq | u8 idx缺片补发请求，对端只重发该片

可靠性语义：发送侧为每条 ≤BT_MCP_CFG_TX_RETRY_BYTES 的消息登记重传槽， ack_tout_ms 未确认则按原 seq 整条重发（最多 retry_max 次）； 接收侧按 seq+len+CRC32 指纹去重（默认 5s 窗口），重复消息只回 ACK 不再上抛。

v0.5 两条重要扩充：

  • 大消息保护：普通 bt_mcp_session_tx() 只保护 ≤BT_MCP_CFG_TX_RETRY_BYTES（默认 512B）的消息。 bt_mcp_session_tx_ref() 改为引用式——槽里只记 (seq, len, 指针)，重传时从调用方缓冲重新编码，因此可覆盖到 MAX_MSG。契约：该缓冲必须在 ACK 或放弃之前保持有效。
  • 拥塞退避：ACK 超时不再是固定值。超时重传时 rto = min(rto×2, BT_MCP_CFG_RTO_MAX_MS)（默认上限 4800ms）； 收到任何合法 ACK 立即回落到基准 ack_tout_ms； NACK 定点补片不退避（对端明确告知缺哪片，不是拥塞信号）。 默认态 rto == 基准，无丢包时行为与 v0.4 逐字节一致。

v0.3 信用改为闭环：每消费对端一条 MCP 消息自动回补 1 credit（饱和 255），宿主无需手工发 CREDIT。

5会话层 L4：状态机与状态门

IDLE ──link_up(token)──▶ LINK_UP ──initialize 完成──▶ READY ▲ │ 允许 RESUME / initialize 粗门 MCP 全量 + CREDIT/PING └──────link_down(bond)────┘◀──────────────────────────────┘
状态允许收允许发门行为（违例返回）
IDLE无（拒收一切）无rx → E_STATE
LINK_UP控制帧 + initialize 形态控制帧 + initialize其他 MCP → 丢弃/拒绝
READYMCP 全量 + 控制帧MCP（受信用）+ 控制—
  • initialize 粗门（LINK_UP 期）：payload 以 initialize / "initialize / {"jsonrpc 前缀开头且 ≥ 9B 才放行。
  • 信用窗口（仅包通道）：每发一条 MCP 消息扣 1 credit（初值 = tx_window，默认 4）；窗口 0 时 session_tx → E_AGAIN，须等对端 CREDIT 回补或 tick 重试。流通道（flow_ctrl=1）免信用。
  • link_up 重置：每次 link_up 重置 credits 与重组状态。
  • RESUME token 绑 bond：断链时 link_down(bond_intact)；bond=0（配对丢失）则 token 清零，之后同 token 的 RESUME_REQ 会被拒绝。

7.2 必须理解的判例：emit 双次调用 vs notify 一体到达

v0.3 起 framer 每片只调用 emit 一次，参数就是完整的帧头+载荷，与 GATT notify / SPP write 的承载单位一一对应。宿主直接把它投进发送队列即可：

  1. 片旁路聚合（HIL 实测配方）：emit 侧记录——收到 6B 头开新缓冲，payload 追加同缓冲；之后每个缓冲一次 framer_feed（= 一个 notify 一次喂入）。M4c 判例：mtu=23 时 84B 消息拆 ≥4 notify，逐 notify 直通 feed 重组成功。
  2. 双特性法：把 6B 头与 payload 各投不同特性（如 Up 特性收头、Dn 收体）——不需要，且浪费一次写事务；仅列出以备栈不支持聚合时。

    uint32_t head, tail;  uint32_t drop;
} bt_mcp_spp_port_t;

int       bt_mcp_spp_port_init(bt_mcp_spp_port_t *p);
uint32_t  bt_mcp_spp_port_used(const bt_mcp_spp_port_t *p);
int       bt_mcp_spp_emit(void *io, const uint8_t *data, uint16_t len);
uint32_t  bt_mcp_spp_drain(bt_mcp_spp_port_t *p, uint8_t *out, uint32_t len);

流通道 feed 无片边界要求：任意字节段（1B~7B 混合切分实测）逐段喂 framer_feed 即完成重组。ring 回绕单调 head/tail 判满判空（40 轮回绕不丢字节实测）。

8接线模式

8.1 设备端（GATT server，跑 core 的 L3+L4+L5）

/* 初始化（一次性） */
bt_mcp_gatt_port_t gp;
bt_mcp_framer_t    fr;
bt_mcp_session_t   sess;
bt_mcp_server_t    srv;

bt_mcp_gatt_port_init(&gp, att_mtu);            /* 247 → cap.mtu=244 */
bt_mcp_frame_cfg_t  fcfg = { .max_reasm = 4, .frag_tout_ms = 2000 };
bt_mcp_framer_init(&fr, &fcfg, &gp.cap);
bt_mcp_session_cfg_t scfg = { 30000, 5000, 4, BT_MCP_ROLE_SERVER };
bt_mcp_session_init(&sess, &scfg);
bt_mcp_session_bind(&sess, &fr, bt_mcp_gatt_emit, &gp);
bt_mcp_server_init(&srv, &sess, &my_tools_cfg, "my-fw", "1.0");

/* —— 蓝牙栈事件 → core —— */
on_connect:      bt_mcp_session_link_up(&sess, token);
on_disconnect:   bt_mcp_session_link_down(&sess, bond_intact);
on_notify_sent:  (无操作；FIFO 由栈自然冲出)
on_char_write:   /* 片聚合后逐片 */ bt_mcp_framer_feed(&fr, chunk, n, /* sink→session_rx→server_rx */);
on_1ms_timer:    bt_mcp_session_tick(&sess, now_ms);

9JSON-RPC 消息集（L5）

method方向处理
initializeC→S应答 protocolVersion（协商回显）+ serverInfo + capabilities + _meta.io.btmcp.chan
notifications/initializedC→S通知（无 id）→ 置 initialized=1，会话进入全量态
pingC↔S应答 pong
tools/listC→S返回工具表（name/desc/inputSchema/authz）
tools/callC→Sparams.arguments 嫁接为工具参数视图；执行 fn → 流式 writer 输出 result
其他 methodC→S-32601 Method not found
未 initialize 即调用C→S-32002（或 E_STATE 门挡在前）
malformed 定位 id—-32700 Parse error

工具参数取值：tools/call 的参数在 params.arguments 嵌套层，core 的 JSON SAX 用 bt_mcp_json_get_sub 把 arguments 片段嫁接成工具视图，工具回调签名不变。响应 writer 零中间 DOM、双层转义。

12GATT 服务定义

特征性质用途
Ctrlnotify + write主数据通道（MCP 帧分片，ATT_MTU−3）
Dn（下行）notify设备→Proxy 方向（可并入 Ctrl 的 notify 侧）
Up（上行）write-no-rspProxy→设备方向

SPP 则在 SDP 注册 SPP UUID、开 RFCOMM 通道，同一二进制零差异运行——唯一区别是 port 填的 bt_mcp_chan_cap_t。L2CAP LE CoC 可选：credit 回调映射到 cap.flow_ctrl=1，L4 免信用。

13集成检查清单

  1. 编译：C99、零 OS 依赖。core 五个 .c（frame/session/json/writer/mcp_server）+ port 两个头，直接编入固件。禁用 GNU 扩展（-std=c99 -Werror 可过）。
  2. cap 正确：GATT mtu = ATT_MTU−3 且 ≥ 20；SPP mtu=0、kind=STREAM。
  3. emit 聚合（仅 GATT）：hdr(6B) 开新 notify 缓冲、payload 追加同缓冲，逐 notify framer_feed。
  4. 状态门：连接事件必须打到 link_up/link_down；断链带 bond_intact；token 绑 bond 持久。
  5. 背压：处理 E_AGAIN（信用耗尽，缓存重发）与 port 的 E_NOMEM+drop（线路缓冲满，需加大 drain 频率）。
  6. 时钟：周期 session_tick(now_ms)；否则半帧超时/RESUME 超时永不触发。
  7. 工具表：const 编译期表 + input_schema_json 字符串 + authz 级别（OPEN/CONSENT/RESTRICTED，授权 UI 由宿主实现）。
  8. 验收基线：参考仓库全量回归 = 1295 项差分（主 1045 + FCS16 配对 196 + 共享模式 54）+ 198 项 port HIL + 626 项单元 + 38 项官方 SDK 互验 + 20 项 golden，全绿；fuzz 帧层 200 万轮零崩溃。最小 E2E 验收 = initialize → notifications/initialized → tools/list → tools/call → ping 全链路（含 mtu=23 分片链路）。
