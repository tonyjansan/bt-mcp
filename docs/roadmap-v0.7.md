# BT-MCP v0.7 及中期里程碑规划

日期：2026-11-12 · 基线：v0.6.0 · 前置：[roadmap-v0.6.md](roadmap-v0.6.md)

## 0. 先校准：现在的真实位置

v0.3–v0.6 把「协议正确性」这条路基本走完了：1295 项差分、198 项 HIL、
11469 项矩阵断言、官方 SDK 互验，行覆盖 95%。**协议语义层面的问题已经很少**，
v0.6 一整轮只抓到 2 个真缺陷（信用死锁、writer 错误语义）。

那还剩什么问题？对着代码与目录实测，答案是**三类「没被真实世界检验过」的东西**：

| 现状（实测） | 含义 |
|---|---|
| `port/bt_mcp/` 只有 3 个头文件适配层，**没有 `examples/` 目录** | 蓝牙行为全是**假设**：MTU 协商、连接间隔、notify 节流、断链语义，一条都没在真实栈上验证过 |
| 无 `Makefile` / `CMakeLists.txt` / pkg-config，只有 `build.sh` | 外部团队接入要自己啃脚本；`build.sh` 是**验证入口**，不是**集成入口** |
| RAM 数字全是 `sizeof()`，无固件实测 | 「COMPACT 档 10.6KB」是结构体大小，不是**真实固件增量**（含栈、libc、port 胶水） |
| 无 `.clang-tidy` / `.cppcheck` / MISRA 基线 | 「零告警」只覆盖 `-Wall -Wextra -Werror`，不含静态分析规则 |
| 单实现 + 单 oracle（Rust），两者都由我写 | 差分能防「两侧漂移」，但**防不了「两侧一起错」**——这个风险从 v0.4 就一直存在 |

**结论**：v0.7 起的主线不再是「加协议功能」，而是**让外部团队能不带我们地把这套东西用起来**。
功能缺口（sampling / completion / templates）属于「规范可选」，优先级低于可信度。

## 1. 中期里程碑：**M1「可交付」（v1.0-rc）**

> **一句话定义**：一个没参与过本项目的嵌入式团队，能照文档在真实硬件上跑通
> MCP over BLE，并复现我们宣称的可靠性数据——**全程不需要作者在场**。

目标周期：**约 8–10 周**（v0.7 / v0.8 / v0.9 三个迭代）。

### 出口判据（全部可测，不做主观判断）

| # | 判据 | 验证方式 | 当前 |
|---|---|---|---|
| E1 | **真实 BLE 栈**跑通 MCP 全链路 | Zephyr/NimBLE 或 ESP-IDF 其一，开发板 + 手机 Host，跑通 initialize→tools/call | ❌ 未开始 |
| E2 | **真实硬件可靠性数据** | 板上跑 ≥1 万条消息，丢包/断链场景下交付率与重复率有实测数字 | ❌ 只有模拟数据 |
| E3 | **标准构建方式接入** | `find_package(bt_mcp)` / `pkg_add` 级体验；外部项目 `add_subdirectory` 即可用 | ❌ 只有 build.sh |
| E4 | **真实固件 RAM/Flash 增量** | 实测 `.text/.data/.bss` 增量，与 `ram_baseline.py` 的预测值比对，误差 ≤15% | ❌ 未测 |
| E5 | **接入文档可用性** | 让一个未参与的人按 §快速开始 在 1 小时内跑通（记录卡点并修文档） | ❌ 未验证 |
| E6 | **第三方实现互验**（第二条腿） | 除官方 TS SDK 外，至少一个**独立 C/Python 实现**能解析我们的输出 | ⚠️ 只有 SDK |
| E7 | 遗留缺陷清零 | 重复投递根因修复；小 MTU 交付率 ≥50%；分支覆盖 ≥75% 或明确放弃并说明 | ❌ 三项未达 |
| E8 | 静态分析零新增告警 | clang-tidy + cppcheck 基线入库，CI 门禁 | ❌ 未开始 |

**E1/E2/E4 是硬门槛**——没有它们，「能为 MCU 跑 MCP」只是我们的自我声明。
**E5 最容易被跳过，但对「可交付」最致命**：东西能跑但别人接不上，等于没交付。

### P0（必须）

| # | 任务 | 已知证据 | 做法 |
|---|---|---|---|
| **A1** | 修「重复投递」根因 | 已实测收窄（2026-11-12）：单轮 118 次投递中接收端**零同 seq 重复** → 去重逻辑正确；残余 1 次是同一内容以**不同 seq** 到达 → 问题在**发送端**，不在去重 | 在 `tx` 侧记录 `(seq, 内容指纹)`，确认是否存在「同一内容二次调用 tx」。重点排除：`E_AGAIN` 重试是否重发已发内容、`slot` 释放后 seq 被复用。**注意**：不要再去改去重窗口，已证明它不是原因 |
| **A2** | 小 MTU 交付率（8% → ≥50%） | MTU23 + 200B 载荷 = 31 片/条，任一片在 `retry_max=3` 内补不齐即整条放弃 | 分片级 SACK（一次 NACK 报多个缺片）或按「剩余片数」自适应 `retry_max`；先做**测量**：统计整条放弃时缺在第几片 |
| **A3** | 分支覆盖 69% → 75%（或正式放弃） | v0.6 已证明「组合矩阵」只到 68%，剩余是**短路条件的边** | 换手段：对每个 `if (a && b)` 用**条件级**测试（让 a 真 b 假 / a 假），而不是继续堆输入组合。若两周内到不了 75%，写进路线图**明确放弃**并改口径为「行覆盖 ≥95% + 不变量测试」 |

### A3 决定：放弃 75% 分支覆盖目标，改为「行覆盖 + 不变量测试」

**决定**：不再追求分支覆盖 75%。理由不是「做不到」，而是**投入产出比已经崩塌**，
且这个指标不再衡量我们真正在意的东西。

**实测数据**（v0.7 本轮）：

| 阶段 | 行覆盖 | 分支覆盖 | 增量 |
|---|---|---|---|
| v0.6 末 | 95.07% | 68.15% | — |
| v0.7 加完 A1/A2/A4/A5 后（新代码无测试） | 93.86% | 68.17% | 行 −1.2（被新代码拉低） |
| 补 `test_branches.c` 初版（47 项断言） | 95.17% | 69.49% | 分支 **+1.32** |
| 补 JSON 转义全字符 + notify 路径（+9 项） | 95.34% | 69.65% | 分支 +0.16 |
| 补 nasty 资源 + image/audio 内容项（+2 项） | 95.51% | 69.80% | 分支 +0.15 |

**边际收益递减得非常干净**：第一轮 +1.32，之后每轮 +0.15~0.16。
按此速率，最后 5 个百分点需要约 **37 轮**同类工作，而每轮要人工读代码
定位「哪个短路条件的哪一侧没走过」。

**为什么这个指标不该继续当主指标**（v0.6 + v0.7 两次验证）：
1. v0.6 时行覆盖已 95%，本轮 A1（重复投递）与 A4（未转义 bug）**都不是
   覆盖率发现的**——前者靠链路仿真 soak，后者靠「清理时盯着代码看」。
2. A5 的 completion 回调契约错误（切片当成 C 串）也是靠**动手写测试**发现的，
   而不是靠覆盖率数字推动。
3. 剩余未覆盖分支集中在两处：(a) 深层错误传播链（`if (rc == X) return Y`
   的每种错误码），(b) 转义函数的逐字符 case。前者用「不变量测试」覆盖更有意义
   （验证「任何 sink 错误都原样透传」比「每个错误码都走一次」更本质，
   而这类不变量测试已存在于 test_fault/test_branches）。

**改口径后我们盯什么**：
- **行覆盖 ≥95%**（仍然是硬门禁，防「新代码没测试」）；
- **分支覆盖 ≥69% 不退化**（门禁从 68 抬到 69，只防倒退，不追高）；
- **不变量测试**为主：soak（零重复/交付率下界）、fuzz（四条不变量）、
  矩阵（失败后可继续服务）、branch 测试（错误码透传契约）。

这条决定本身就是 v0.6「覆盖率不该继续当主指标」结论的**第二次验证**。

### 顺带修掉的一个「文档撒谎」

`trace.h` 声称「`BT_MCP_CFG_TRACE=0` 时 `bt_mcp_trace()` 展开为空，零代码零 RAM」，
但它其实是**函数**——调用点仍生成 call 指令。8 个调用点共约 **456B**
（session −406B + server 其余）。改成宏后承诺才成立，且关闭档真实省下 456B。
这类「注释比实现乐观」的问题不会被测试发现，只能靠量体积。

### E4 的诚实结论

`tools/footprint.py` 用宿主 clang 量，**不是** `arm-none-eabi-size`。
能信的是相对关系（哪个开关贵、贵多少）；不能信绝对值
（ARM/Thumb 与 x86-64 指令密度差 1.5~2x）。**E4 仍未达成**，
但「FCS16 ≈ +1200B」「档位只改数组不改代码」这类结论是可迁移的。

| # | 任务 | 设计与验收 |
|---|---|---|
| **B1** | **选一个真实栈落地**（推荐 Zephyr/NimBLE） | 不做「三平台都支持」，只做**一个做到能上板**。验收：开发板 + 手机 nRF Connect / 自写 Host，跑通 initialize→tools/list→tools/call，附抓包与日志 |
| B2 | port 层从「头文件适配」升级为「可移植层 + 参考实现」 | 现有 `port/bt_mcp/*.h` 是纯 header，真实栈需要 .c 胶水（连接回调、MTU 交换、notify 队列）。把**胶水的接口契约**固化，参考实现放 `examples/zephyr/` |
| B3 | 真实固件 RAM/Flash 实测（E4） | 用 `arm-none-eabi-size` 量 demo 固件增量；与 `ram_baseline.py` 比对，误差 >15% 就要修正基线口径（说明 `sizeof()` 漏了什么） |
| B4 | 板上可靠性测试（E2） | 板上跑 1 万条 + 人为断链/干扰；产出「交付率 / 重复率 / 平均 RTT / 重传次数」四组真实数字，替换 README 里的模拟数据 |
| B5 | CMake + pkg-config（E3） | `add_subdirectory` / `find_package` 两种接入；`build.sh` 保留为验证入口。验收：新建一个空工程，5 行 CMakeLists 用起来 |

**关键取舍**：B1 只做一个平台。三平台并行是「看起来全面，实际上每个都没上过板」——
这正是当前 `port/` 目录的问题。**一个能上板的 port 胜过三个 header。**

## 5. 明确「不做」的事（避免范围蔓延）

| 不做 | 理由 |
|---|---|
| OAuth / 认证授权框架 | 规范可选；蓝牙配对 + 应用层 consent 已够当前场景，企业需求另议 |
| 三平台并行 port | 见 B1 取舍：一个上板 > 三个 header |
| WASM / 浏览器模拟器 | 对「可交付」里程碑无贡献，属于开发者体验优化，放 v1.x |
| 8/16 位 MCU 的 `uint64_t` 收敛 | 只有 unsigned 整数进度的 3 处；收益 < 改动风险，等有真实 8 位需求再做 |
| 追求分支覆盖率数字 | v0.6 已证明边际收益崩塌；改为「不变量测试 + 行覆盖」为主 |

## 6. 依赖与风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **没有真实硬件**（当前环境） | E1/E2/E4 全部阻塞 | 这是里程碑的**唯一硬依赖**。若两周内拿不到板子，v0.8 退化为「写移植指南 + 用 BlueZ 在 Linux 上跑通」（至少是真实协议栈，虽非 MCU） |
| NimBLE 集成工作量被低估 | v0.8 延期 | 先做「最小可跑」：单连接、无 RESUME、固定 MTU；把这版跑通再补特性 |
| A2（小 MTU）可能需要协议改动 | 影响兼容性 | 分片级 SACK 是**新增控制帧**，需同步 oracle + 版本协商；若改动过大，降级为「自适应 retry_max」（纯本地策略，零协议影响） |
| 单人开发 + 无外部评审 | 「双侧一起错」风险 | C2 的独立解析器就是为此设计；另可邀请外部做 1 次协议走查 |
