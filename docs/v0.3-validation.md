## 2. 修复的问题（按严重度）

### P0 — 协议不可用 / 死锁

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | 包通道丢片即丢整条消息（无重传） | GATT 不可用 | L3 缺片保持槽 + 登记 NACK；L4 重传槽环 + ACK/NACK + 超时整条重传 + 接收去重 |
| 2 | 信用不闭环，发满窗口永久 `E_AGAIN` | 会话必然死锁 | 消费即累计回补；发送失败不扣；放弃重传退信 |
| 3 | `initialize` 回 `serverName` 平铺、无 `serverInfo`、无 `_meta` | 标准 Host 握手即失败 | 回 `protocolVersion`（协商回显）+ `serverInfo{}` + `_meta.io.btmcp.chan` |
| 4 | 字符串 id 被 `strtoll` 成 0，且越界读 | 请求-响应无法关联 | `id_is_str` + 原文片段回显；i64 定长饱和解析 |
| 5 | FCS16 收发线序不一致（v0.3 重构引入） | 该模式所有帧 CRC 失败 | 统一 `hdr|FCS|payload`，流通道补 FCS 状态机与校验 |
| 6 | 流通道一次畸形帧后永久卡死 | 通道需重启 | `stream_desync()` 复位后重新找 magic |

## 3. 新增能力

- **Bridge 侧客户端**（`mcp_client.h/.c`）：与设备端共用同一 core，主动握手、
  请求表、id 匹配、超时上抛、通知回调——Bridge 可跑在嵌入式网关上而不只是手机。
- **`bt_mcp_session_feed()`**：port 一行把收到的字节喂进协议栈。
- **开销基线**（`tools/bench.c`，实测）：
  - MTU 244 时 512B 消息放大 1.04×；MTU 23 时 1.36×（**MTU 是首要旋钮**）
  - 流通道固定 +6B；不可靠包通道控制帧开销 3.1%

## 4. 已知限制（明确记录，非静默降级）

1. 大于 `BT_MCP_CFG_TX_RETRY_BYTES`（默认 512B）的消息在不可靠包通道上**不享
   重传保护**，需应用层兜底或改走 resources 分页。
2. `idx` 是 u8 → 单消息最多 255 片；在 23B ATT_MTU（chunk 14B）下有效消息上限
   约 3.5KB，小于 FULL 档的 8KB 声明。
3. 信用计数基准随 `link_up` 重置，前提是「断链是双向事件」。port 若单边重连，
   窗口最多饱和到 255 并以 `E_NOMEM` 背压，不会崩溃但属 port 违例。
4. FCS16 目前只有 C 侧往返测试与 fuzz，尚未纳入 C↔Rust 差分矩阵。
5. 真实芯片移植（Zephyr/NimBLE）与手机 Bridge 仍是待办。

## 5. 复现方式

```sh
./build.sh              # 全部套件
./build.sh 500          # 加大随机轮数
./build.sh 150 asan     # ASan/UBSan 差分

cc -O2 -std=c99 -Icore/include -DBT_MCP_FUZZ_MAIN \
   fuzz/fuzz_frame.c core/src/frame.c -o build/fuzz_frame && ./build/fuzz_frame 3000000
```
